# Tune first release

## Goal Capsule

- **Objective:** Deliver a standalone DSPy-style library above ReqLLM. Developers
  can inspect structured prompts, tune programs for a fixed model configuration,
  compare results, and load learned parameters into application code.
- **Means:** A small Elixir core, immutable parameters, ordinary function
  composition, pure prompt adapters, and explicit evaluation and optimization.
- **Authority:** Revise planning documents only. This plan is for Mike's review.
  Feature implementation, provider calls, commits, publication, and changes to
  sibling repositories require a later request.
- **Stop conditions:** Finish at a checked plan. During later implementation,
  report a missing public ReqLLM contract to its owner; do not copy provider logic.
- **Next executor:** An implementation worker after Mike approves the plan and
  authorizes implementation. Readiness describes the plan, not built features.

## Product Contract

### Summary

`tune`, under `Tune`, is an independent Mix library. It
supports broad prompt and example optimization with an idiomatic Elixir API.
The core stays small even though the first release includes all 15 prompt and
example targets below. Jido is an early consumer, with no required Jido dependency.

The design interview is complete. Mike confirmed the design and requested this
plan revision. Documented algorithm behavior is the compatibility target. Exact
seeded parity and every upstream option are not required. Document differences.

### Problem Frame

Developers need to inspect and improve task prompts for specific models without
adopting Imp's provider layer, agent runtime, training system, or protocol stack.
Keep one owner for each boundary. ReqLLM owns provider behavior; this package owns
task parameters and optimization; the application owns its code and runtime policy.
There is no unmeasured claim about code size, speed, cost savings, or model quality.

### Actors

- Developers define typed predictors and compose them in Elixir code.
- Evaluators supply examples, metrics, and explicit dataset roles.
- Optimizers return new parameter values and reports.
- Applications supply code, model configuration, credentials, and host policy.
- Mike reviews the implementation plan and later authorizes implementation.

### Requirements

| ID | Required behavior |

### Key Flows

1. Define a signature and predictor. Select a target configuration. Prepare an
   inspectable prompt, execute through ReqLLM, parse and validate, and retain the
   response with the result.
2. Compose evidence extraction and answering through named calls. Each call
   returns updated execution state; labels remain outside program inputs.
3. Build examples from training data, or search candidates using training and
   explicit validation data. Score candidates under the same target configuration.
4. Stop at a completed search or limit. Return an eligible result or a reported
   failure. Run final test evaluation through a separate call.
5. Export parameters and provenance. Validate the artifact against fresh
   application code and apply all updates atomically. Supply runtime configuration
   explicitly when running the loaded program.
6. A host prepares a request, applies its own controls, executes it, and finishes
   locally. Repair or extraction requires another explicit program step.

### Acceptance Examples

- **A1:** One classifier works through Chat, JSON, and XML. Equivalent valid
  replies produce the same typed map. Missing input makes zero requests. An
  invalid or incomplete reply produces a retained error, not a partial success.
- **A2:** Grounded QA extracts facts from supplied context, then answers with
  source identifiers. Training labels cover the final answer; successful teacher
  traces supply examples for both predictors. Inspect both rendered prompts.
- **A3:** If answering fails, the partial extraction trace is retained but cannot
  become an accepted bootstrap trajectory. Runs and candidates remain isolated.
- **A4:** A versioned artifact reloads into fresh application code with the same
  learned values and provenance. A parameter or schema mismatch applies nothing.
- **A5:** A host stub executes each prepared request once. Finish makes no model
  request. Host denial cannot produce a successful step or bootstrap example.
- **A6:** A failed validation row makes a candidate ineligible. An explicit
  failure_score supplies its numeric penalty while the error remains visible.
  Missing validation data fails before search; test rows never enter optimize.
- **A7:** A budget that expires during proposal or evaluation cannot promote a
  partial candidate. Return the previous eligible incumbent, or an error and
  report if no incumbent completed. Account for every managed role.
- **A8:** Every first-release target has a scripted behavior proof and a source
  comparison entry. Reports separate observed scores from algorithm claims.

### Success Criteria

All requirements have mapped offline proof. The QA example uses public APIs to
run, evaluate, optimize, inspect prompts, and reload parameters. Comparison output
shows baseline and optimized scores, eligibility, parse success, logical calls,
and reported token use for each fixed model/adapter configuration.

Automated tests need no credentials, Python runtime, or live provider. Real-model
comparisons are a separate, explicitly invoked example; executing paid or live
calls is not part of this planning request. Report measured outcomes without
requiring every optimizer to improve every model.

### Scope Boundaries

Included: JSON-compatible named fields; typed predictors; explicit composition;
Chat, JSON, and XML adapters; numeric metrics with optional text feedback;
evaluation; all first-release targets; versioned parameter artifacts and
provenance; host preparation/completion; the QA example; documentation and checks.

A scalar or array can be a named field. Image, audio, and file inputs are deferred.
Weight training, BootstrapFinetune, GRPO, the full BetterTogether workflow, and
Flex-style program structure search are deferred. They remain future targets.

The current package must require no Python runtime for installation, compilation,
execution, or default checks. Do not bundle or start Python workers. Do not add
Nx, Axon, an agent runtime, ReAct/RLM, code execution, tools, vector stores, global
settings, a workflow engine, a macro DSL, or a Jido dependency to satisfy this
release. Actual Jido integration, whole-program serialization, Imp artifact
compatibility, and publication remain separate work.

### Key Decisions

- Keep a separate optional package and a small normalized core.
- Include all prompt and example targets in the first release, not only the
  initial example-building pair. Use Elixir for statistical search.
- Match documented behavior, expose a small API, and publish a differences table.
- Make model roles, adapters, dataset roles, failure penalties, and limits explicit.
- Keep adapters pure. ReqLLM owns transport retries; repair/extraction is composition.
- Keep code and credentials in the application. Artifacts hold data and provenance.
- Use the QA example and offline tests as the reference proof.

### Rejected Alternatives

- Copy Imp's complete runtime and public API: these exceed the package's role.
- Add this layer to ReqLLM core: provider-only users need no optimizer dependency.
- Hide fallback calls inside adapters: this defeats inspection and call accounting.
- Copy Python APIs and random-number behavior: this adds work without the selected
  compatibility benefit.
- Select on training or test data by default: dataset roles must stay explicit.

### Dependencies

The scaffold has one direct dependency: published `req_llm ~> 1.30`, locked to
1.30.0. It has no supervisor and no feature implementation. The declared Elixir
floor is `~> 1.18`, matching the resolved LLMDB requirement. Prior scaffold checks
used Elixir 1.20.4 / OTP 29; that is not evidence for the minimum runtime.

Add dependencies only with their first use during implementation: compatible Zoi,
Splode, and Jason in U1, plus Req for Req.Test and test-only Plug. Zoi 0.19.0,
Splode 0.3.3, Jason 1.4.5, and Req 0.7.5 are already locked through ReqLLM.
Declare Req without `only: :test`; ReqLLM needs it in every environment, and a
narrower top-level `only:` would diverge from that requirement. Add OTP `:crypto`
when U5 uses fingerprints. Add Credo, Dialyxir, and ExDoc with U6's final gates.
Use constraints compatible with the existing lockfile. No dependency is added by
this planning revision. Statistical search and XML delimiters need no Python or
new numerical runtime.

### Current System

The project is a Mix scaffold in the monofolder, with no Git repository of its
own. It contains a manifest, lockfile, formatter, an empty documented facade,
ExUnit startup, README, and local rules. There are no behavior tests or features.
Current `mix quality` runs formatting and compilation only.

ReqLLM at `2d829031` supplies useful patterns: `Router.Request.new/2` normalizes
with Zoi and uses tagged results; `Context` owns normalized messages; `Output`
and `Response` own structured response handling; Splode defines structured errors.
The published 1.30.0 source in the scaffold's ignored deps directory independently
confirms the required public output and response functions.

Imp's adapters, bootstrap traces, Elixir TPE policy, and parameter optimizers show
why typed intermediate records and plain parameter values are needed. Its provider
cache, training workers, capability framework, agent types, and audit workflow
are not dependencies of this design.

Jido's inspected `CallModel` path at `15698ccc` applies budget, context, client,
and telemetry controls. Direct Tune.run inside an Action does not automatically
use that path. U6 proves a host seam; actual Jido integration needs its own proof.

### Target System

```text
application code + named parameters + explicit model configuration
  -> prepare and inspect -> ReqLLM call -> parse and validate -> Result
training + validation + metric + explicit call limit
  -> immutable candidates -> complete eligible incumbent + report
parameters + approved provenance -> versioned JSON -> validate -> updated code value
```

All interfaces below are proposed implementation contracts, not existing APIs.
Use `Tune` as the namespace; short module names in this plan are relative
to it. Constructors return tagged results. Keep one normalized representation.

| Interface | Contract |
| --- | --- |
| `Signature.new/1` | Validate ordered named Zoi input/output fields and instructions. Return a signature. |
| `Predictor.new/1` | Validate a signature and compatible demonstrations. Return an immutable predictor. |
| `Parameter.new/1` | Validate one named text/JSON value against its Zoi schema. Used only for extra tunable task data. |
| `ModelConfig.new/1` | Normalize a ReqLLM model reference, an explicit adapter module/options, and ReqLLM request options. |
| `Adapter.render/4` | Pure callback: signature, demonstrations, inputs, options to a rendered ReqLLM context and output descriptor. |
| `Adapter.parse/3` | Pure callback: signature, text or projected JSON reply, options to a field map or parse error. |
| `Predictor.prepare/3` | Purely validate inputs and render with the explicit adapter. Return Prepared without credentials or model execution. |
| `Predictor.finish/2` | Check a Prepared value against a ReqLLM.Response; parse, validate, and return a Step or error locally. |
| `Tune.run/3` | Program or predictor, input map, runtime options to `{:ok, result}` or `{:error, error}`. Runtime ExecutionError retains the original cause and partial Result. |
| `Execution.predict/3` | Resolve a named predictor, use the execution's active role, and return output plus updated execution. Application code never names a role. |
| `Execution.value/2` | Read a declared JSON Parameter from the current candidate; no model call. |
| `Tune.evaluate/3` | Program, examples, options to an evaluation report or setup error. No optimization or dataset splitting. |
| `Tune.optimize/2` | Program and options to `{:ok, updated_program, report}` or `{:error, optimization_error}`. Runtime failures carry their report and original cause. |
| `Optimizer.compile/3` | Small behaviour: optimizer configuration, program, normalized optimization context to a new program/report or reported error. No capability registry. |
| `Parameters.dump/2`, `encode/1`, `decode/1`, `apply/2` | Extract approved parameters/provenance, exchange versioned data, validate, and apply atomically to supplied code. |

Constructors and run/evaluate return `{:ok, value}`. `Tune.optimize/2` and
`Optimizer.compile/3` deliberately return `{:ok, program, report}`, because a
limited search returns both an incumbent and its incomplete report.

Composite application structs implement four Program callbacks: `signature/1`,
`parameters/1`, `put_parameters/2`, and `call/3`. `parameters/1` returns one map of
unique string names to Predictor or Parameter values. `put_parameters/2` returns
an updated struct of the same module. `call/3` receives program, normalized inputs,
and Execution; it returns output and updated Execution, or an error with Execution.
A standalone predictor uses the name `"root"`.

This replaces the draft's separate predictors/put_predictor callbacks before
there are callers. It gives Playbook and Optimize.Anything a typed JSON value
without a second component framework. Application code decides how a value is
used; Execution distinguishes prediction from reading a value.

### Key Technical Decisions

#### KTD1 — Normalize typed task data once

**Decision:** Store ordered field definitions with trusted string names, Zoi
schemas, and descriptions. Accept existing atom names at construction and convert
once; reject duplicate names and atom/string collisions. Use XML-safe identifier
names for declared fields. Nested JSON object keys remain data. Input/output
values use string-key maps; normalize trusted atom input keys once and create no
atoms from external data.

Use Zoi-backed structs as ReqLLM.Router.Request does. Support JSON-representable
strings, finite numbers, booleans, nulls, arrays, nested objects, enums, and nullable
fields. Reject unsupported transforms and nonportable values before rendering.
Preserve declared field order for prompts. Export schemas with public
Zoi.to_json_schema; do not call private ReqLLM schema helpers.

**Reason:** R1-R3 need one contract across formats, traces, and artifacts.
**Rejected alternative:** Multiple signature syntaxes or independent type systems.
**Consequences:** No string-signature parser or macro DSL. Test string-key Zoi
fields with the locked version. **Governs:** U1, U2, U5, U7.

#### KTD2 — Pure format adapters above ReqLLM

**Decision:** Adapter callbacks render and parse only. Prepared retains normalized
inputs, signature identity, adapter/options, context, and output descriptor.
Direct execution composes prepare, public ReqLLM.generate_text/3, and finish.
Use text output for Chat/XML. JSON supports explicit text or structured mode;
structured mode passes the exported JSON schema to ReqLLM.Output.object and uses
strict public Response.output_result validation. ReqLLM owns provider support.
There is no automatic switch of mode, adapter, or model after a failure.

Managed requests pass `json_repair: false`. ReqLLM enables light JSON repair by
default and can also report `:legacy_type_coercion`; either would change a value
without an explicit program step. Treat any nonempty `Output.Result.repairs` list
as a parse failure that retains the result as evidence. Text-mode adapters parse
the raw response text and never consult ReqLLM's repaired projection.

Chat uses DSPy field markers and completion framing. JSON uses its documented
object format. XML follows DSPy 3.5's schema-directed delimiters, including nested
values and unescaped text/code; it is not a general XML document parser. Do not
expand entities or load DTDs. Keep parsing bounded and reject missing, duplicate,
ambiguous, or invalid fields. Parse primitives according to the declared type;
validate every resulting map against the same Zoi output schema.

Before success, require no response.error or refusal and a completed response.
Accept `:stop`; accept `:tool_calls` only for ReqLLM's materialized, validated
structured-output mechanism. This package executes no tools. Reject truncated,
filtered, cancelled, incomplete, unknown, and missing finish reasons. Retain the
original response and validation evidence. Store provider failures unchanged as
the cause in an execution or optimization error; package parse/validation errors
use small Splode errors. ExecutionError carries the partial Result, so callers
can inspect completed steps after a later stage fails.

**Reason:** R1, R2, R7 require inspection and one transport owner.
**Rejected alternative:** Hidden JSON fallback, extraction LM, or repair retry.
**Consequences:** Repair is another named program step. Compare formats by measured
score, parse success, and tokens; XML has no assumed token advantage.
**Governs:** U1, U7, U6.

#### KTD3 — Explicit composition and typed parameters

**Decision:** Execution is an immutable per-run value with named parameters,
normalized runtime, active model role (KTD9), remaining allowance, and ordered
steps. Thread it with normal
Elixir control flow. Steps retain actual inputs, outputs, signature/name, model
role, and ReqLLM.Response. Results retain final output and ordered steps. Failures
retain partial records and cannot supply successful bootstrap trajectories.

Predictor instructions live in its signature; demonstrations are its other
learnable data. A Parameter holds a schema and JSON value, such as a lesson list
or candidate text. There is no duplicate instructions field, global trace store,
process dictionary, registry process, or reflection over arbitrary application
structs. A Program callback supplies the declared map explicitly.

**Reason:** R3, R5, R6 need immutable named changes, including non-prompt JSON data.
**Rejected alternative:** A second generic component/plugin system for two value
optimizers. **Consequences:** Only declared parameters and calls through Execution
are managed. Host callbacks and their external work remain host-owned. First-release
program steps are sequential. **Governs:** U2, U4, U9, U10, U17, U18.

#### KTD4 — Explicit data roles, scores, and eligibility

**Decision:** A metric receives Example and Result and returns a finite number or
`%{score: number, feedback: binary_or_nil}`. Normalize once into a Metric value.
No 0..1 restriction or automatic rescaling. Reject invalid scores and callback
failures as row errors. An empty dataset is a setup error.

`Tune.evaluate` and the package's Evaluation reports are unrelated to
`ReqLLM.Evaluation`, which is a model-graded question call. A metric may call it
as ordinary host code; that call is outside managed call accounting under KTD8.

Continue evaluation after row failures. Retain original row identity, error,
outputs, feedback, and attempted-call evidence. Without failure_score, failed
rows have no fabricated score and make the candidate ineligible. Report successful
row mean and coverage with aggregate selection_score nil. With explicit finite
failure_score, include that value in the mean across all rows, retain errors, and
allow eligibility only after all rows completed or produced recorded failures.
A run-level budget interruption is partial evaluation, not a penalized row.

Candidate-search optimizers require nonempty training and validation datasets as
applicable to their algorithm; no automatic split or training fallback. Training
informs proposals; validation selects. Only Tune.evaluate accepts test data.
Reject testset in optimize options. Detect exact normalized duplicate inputs across
training and validation before search; report a split error rather than silently
filtering or moving rows. Do not claim detection of semantic overlap.

A candidate becomes returnable only after its full validation pass and eligibility
check. Minibatch observations may guide search but cannot become the returned
incumbent. Compare mean scores; keep the earlier candidate on a tie. Store split
identity and candidate lineage so feedback and scores remain associated correctly.

**Reason:** R4, R5, R8 require honest comparisons for arbitrary numeric metrics.
**Rejected alternative:** Zero on every error, silent omission, or test-set search.
**Consequences:** Metrics need no arity/capability dispatch. Example builders may
use training alone and return a complete unscored build; they claim no validation
improvement. **Governs:** U3, U4, U8, U11-U18.

#### KTD5 — Concrete algorithms on a small shared context

**Decision:** Use a minimal optimizer behaviour and explicit module dispatch.
Share normalized examples, parameter replacement, evaluation, proposal calls,
logical-call accounting, and reports. Add a helper only when a second concrete
algorithm needs it. Ensemble is an ordinary program constructor; do not add a
capability registry to make it look like a search algorithm.

Keep finite trial/round/example limits and explicit local :rand state. Statistical
search uses a small categorical TPE implementation for demo/instruction indices;
random search is not a substitute for Bayesian search. Preserve proposal, score,
lineage, eligibility, and stop evidence. Use an explicit accept_score where an
algorithm needs an absolute passing threshold; scores have no universal range.

**Reason:** R5 requires broad behavior without Python or a broad framework.
**Rejected alternative:** One universal search engine or copied upstream settings.
**Consequences:** The inventory below is normative. The source comparison table
must identify implemented rules, deliberate differences, and unsupported options.
**Governs:** U4, U8-U18, U6.

All model calls, including internal typed proposal predictors, use KTD8/KTD9.

Bootstrap admission requires whole-program success even when failure_score allows
ranking a failed candidate. Project actual step fields, validate them, and keep
the final successful call per repeated predictor in an accepted trajectory.
Normalize exact duplicate training rows once and report their count. Use cache
options explicitly for teacher trials; do not imply a seed changes provider output.

Each row's behavior reference is the pinned DSPy source, the pinned `gepa` or
Optuna source it delegates to, or Imp at `748317df` for Imp-specific targets.

KNN uses a pure supplied distance/vectorizer or a small bag-of-words default;
there is no implicit embedding service. Its pool is declared JSON task data;
vectorizer code stays in the application. Per-input bootstrap uses explicit
teacher configuration and the same execution budget, including when called inside
candidate evaluation. A standalone call that performs this optimization also
requires an explicit call limit.

Avatar operates on declared predictor instructions and ordinary Program traces;
it does not require an Avatar agent runtime. Playbook is a lesson parameter,
not serving memory. Its first release omits Imp's separate promotion/audit workflow
and checkpoints; document this adaptation. Optimize.Anything operates through a
normal parameterized Program rather than a second seed/evaluator framework.
The example shows how application code uses the candidate value in named calls.

#### KTD6 — Versioned parameter data and approved provenance

**Decision:** Artifact version 1 stores named entries of kind predictor or value.
Predictor entries contain signature identity, instructions, and demonstrations;
value entries contain schema identity and JSON value. Fingerprint canonical field
names/order and JSON schemas, excluding tunable instructions and values. Strip
`description`, `title`, and `examples` keywords from schemas before
fingerprinting, so editing field prose does not invalidate a saved artifact.
Visit schema positions only; preserve object property names and literal data,
including properties named `description`, `title`, or `examples`.
Field descriptions are code-owned prompt text, not learned parameters. Use one
canonical JSON encoding and SHA-256. Code supplies schemas and callbacks on load.

Provenance contains version/source identity, model and adapter identifiers,
approved non-secret settings, optimizer name/settings, seeds, dataset fingerprints,
evaluation summaries, eligibility, call/usage totals, and stop reason. Use explicit
field allowlists. Never encode raw runtime options, credentials, functions,
processes, response objects, or arbitrary report structs. Provenance is descriptive;
it does not choose models, load modules, or override supplied runtime configuration.

Decode string keys, reject unknown kinds/fields/versions, enforce byte and entry
limits, match the complete declared name/schema set, validate all values, then
apply once through put_parameters. A failed load returns no partial update.
Caller code owns file access. Declared task data and feedback may contain private
text; do not claim content-based secret removal.

**Reason:** R6 and R9 need inspectable model-specific results without executable
serialization. **Rejected alternative:** Whole-program terms or generic struct
encoding. **Consequences:** Local rules already distinguish tunable parameters
from approved provenance. A reloaded KNN program still needs an explicit teacher
configuration and call limit at run time; the artifact guide states this.
**Governs:** U5, U6.

#### KTD7 — Host controls remain outside learned state

**Decision:** Prepare and finish are pure and contain no credentials. The host
chooses its fixed model configuration, applies guards and budget, executes through
its inference path, and supplies the response. Host instructions, authorization,
sessions, tools, and lifecycle are not learnable parameters. Direct run is a thin
ReqLLM path, not evidence that Jido controls were applied.

**Reason:** R7 requires independent use and a viable early Jido consumer.
**Rejected alternative:** A callback advertised as a complete Jido integration.
**Consequences:** U6 proves host denial and one execution with a stub. Actual Jido
integration is a later task in its own repository. **Governs:** U1, U2, U6.

#### KTD8 — Explicit limits and complete incumbents

**Decision:** A model-calling optimization requires max_model_calls, a nonnegative
integer. Count every managed invocation across target, teacher, and proposal,
including failures and evaluation calls. Check/decrement before dispatch. Zero-call
constructors need no budget. A zero budget cannot start a model request.

First-release optimization runs sequentially and threads one run state through
proposal, teacher, and evaluation. Standalone evaluation may use bounded row
concurrency, default 1, under a temporary Task.Supervisor with cleanup. There is
no permanent scheduler, shared budget service, checkpoint/resume, or async job API.

Keep attempted calls, provider-reported tokens/cost, and HTTP retries distinct.
The call limit covers Execution-managed invocations; arbitrary work inside host
callbacks, including metrics, is outside that accounting. Document this boundary.
The library itself makes no model call outside the managed path.

Program execution has a finite step limit, default 32, and a cooperative monotonic
deadline, default 60 seconds. Check before/after calls and pass remaining time as
ReqLLM's `:total_timeout`, the whole-call deadline including transport retries.
Leave `:receive_timeout` as caller-supplied inactivity policy; it does not bound
the call. If the caller sets a smaller `:total_timeout`, use the smaller value. Evaluation enforces a hard row timeout with a worker;
direct execution cannot interrupt arbitrary application code between calls.

Reserve a row's maximum allowance before a worker starts. If a killed worker
loses its returned counters, stop further calls and record the reservation as an
upper bound, not observed usage. This preserves the ceiling without a global
counter. Preserve any earlier complete eligible incumbent.

On budget exhaustion, return that incumbent with stop_reason budget_exhausted,
complete? false for the search, and partial candidate/row records. If none exists,
return an OptimizationError with cause and report. Normal algorithm completion
sets complete? true; a limited search never claims completion. An unfinished
example builder without an evaluated incumbent returns an error/report on limit;
a complete unscored build can return normally without claiming score improvement.

**Reason:** R10 and R4 require useful stopping without partial-candidate promotion.
**Rejected alternative:** Throw away the incumbent, infer costs from call counts,
or continue after unknown worker accounting. **Consequences:** Document limit
semantics once and prove them across roles. **Governs:** U2, U3, U4, U8-U18.

#### KTD9 — Fixed explicit model roles

**Decision:** Normalize one target ModelConfig for each run. It includes an
explicit adapter/options and ReqLLM request options. Teacher and proposal are
separate configurations required only when an algorithm uses them; do not silently
copy target configuration into those roles. Resolve model references through
public ReqLLM APIs and pass provider options through to ReqLLM.

Execution carries one active role, `:target` by default. An optimizer that runs
the application program as a teacher starts that Execution with active role
`:teacher`; the same unchanged `call/3` code then predicts with the teacher
configuration. Internal proposal predictors run in their own Execution with
active role `:proposal`. All three share the run's call allowance. There is no
per-call role argument in application code, so a program cannot mix roles.

Freeze configurations for the run. Optimizers change task parameters only. Reject
options that override the prepared output contract or bypass its validation.
Reject ReqLLM output_repair callbacks and caller `json_repair: true` in managed
requests; repair belongs in an explicit step, and such a callback could hide
another model call.
Another target, adapter, or generation setting means another explicit run.

**Reason:** R9 requires interpretable per-model tuning and separates credentials
from learned state. **Rejected alternative:** Global settings, automatic routing,
or hidden role defaults. **Consequences:** Provenance identifies each role without
serializing runtime secrets. **Governs:** U1, U3, U4, U5, U8-U18.

### Rollout and Recovery

This is a new opt-in library. There is no service or database migration. An invalid
artifact leaves supplied code unchanged. An invalid candidate leaves the incumbent
unchanged. A limited run returns its complete eligible incumbent or a reported
error. Callers choose when to install parameters. Publication and Jido deployment
remain outside this plan.

### Risks and Assumptions

- Schema validity does not prove factual correctness. QA metrics check expected
  answers and supporting source identifiers; real outcomes remain measurements.
- Fifteen targets are substantial work. Keep each behavior slice separate; no
  placeholder algorithm can satisfy the inventory merely by sharing a name.
- Native TPE and schema-directed XML require focused proofs. Exact upstream RNG
  behavior and a general XML engine would add work without the selected benefit.
- Named callbacks can perform arbitrary application work. Managed call/deadline
  limits cannot control side effects outside Execution; do not advertise otherwise.
- Actual prompts, feedback, examples, and lesson values can contain application
  text. Keep full traces local to returned results by default. Artifact projection
  is explicit; ordinary logs/telemetry contain no prompt content by default.
- Strict split checks detect exact normalized overlap only, not paraphrases or
  source-group leakage. Applications own domain-specific split quality.
- Structured JSON provider support belongs to ReqLLM. Return its failure or use
  an explicitly configured text mode in another run; add no provider heuristics.
- The host stub proves the seam, not Jido guards. The later adapter must exercise
  Jido's actual inference path.
